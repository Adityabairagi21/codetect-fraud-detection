# CoDetect – Financial Fraud Detection With Anomaly Feature Detection

**Stage 1: machine-learning pipeline (Jupyter Notebook)**

CoDetect compares two Isolation Forest anomaly detectors on real (synthetic, labelled)
financial transactions:

1. **Transaction-only.** Uses features of the transaction itself and the sender/receiver history.
2. **Graph-enhanced.** Uses the same features plus relationship features from a directed
   transaction graph built with NetworkX.

The question is whether graph relationship features change anomaly-detection quality.
The project reports the measured result whichever way it goes.

> **Status (2026-11-21).** Stage 1 is built: data pipeline, leakage-safe features, both Isolation Forests,
> evaluation, saved artifacts and the inference module. The Flask application (Stage 2) comes next.
> Results are in the executed notebook, `outputs/metrics/` and `models/model_metadata.json`.

### Method in one paragraph
* **Data and split.** IBM AML HI-Small. Sep 1 is warm-up, Sep 2–6 train, Sep 7–8 validation, Sep 9–10 test, and
  the Sep 11–18 simulation tail is excluded.
* **History features.** Every history feature of a transaction uses only the previous 24 hours, strictly earlier minutes.
* **Models.** Model 1 uses 11 transaction features; Model 2 adds 10 graph features.
* **Model selection.** Each Isolation Forest picks its encoding (one-hot / frequency / numeric-only) and settings by
  validation PR-AUC.
* **Scores and risk.** Scores are training-percentile ranks (0–100), and risk levels cut at 90 / 97 / 99.5.
* **Explanations.** Top-3 abnormal features: −log10 tail probability against the training distribution.

**Revision disclosure.** The first version used one-hot encoding only, and its test scores were computed once before
it was revised. The revision was decided from validation evidence alone. Those first-version results were archived
unopened, and both versions are reported in the notebook.

## 2. Dataset

**IBM Transactions for Anti-Money Laundering (AML)**, HI-Small variant
(the higher illicit ratio, small size). Licence: CDLA-Sharing-1.0. All transactions are synthetic,
generated by IBM's multi-agent simulation, and contain no real individuals.

* Official project: https://github.com/IBM/AML-Data. This repo contains **only a README**.
  It links to the data on Kaggle ("new and improved") and to an older copy on IBM Box.
* Data host: https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml

### Schema (verified by `scripts/inspect_dataset.py`)

| Raw column | Canonical name | Notes |
|---|---|---|
| Timestamp | timestamp | `YYYY/MM/DD HH:MM`, minute resolution, **file not time-sorted** |
| From Bank | sender_bank | numeric code with leading zeros, so read as text |
| Account | sender_account | hex id. An account id is unique only *within* a bank |
| To Bank | receiver_bank | as above |
| Account (2nd) | receiver_account | the header repeats `Account`, so pandas reads it as `Account.1` |
| Amount Received / Receiving Currency | amount_received / receiving_currency | |
| Amount Paid / Payment Currency | amount_paid / payment_currency | 15 currencies, including Bitcoin |
| Payment Format | payment_format | ACH, Cheque, Credit Card, Cash, Wire, Reinvestment, Bitcoin |
| Is Laundering | label | **evaluation only, never a model input** |

The mapping is defined once in `config.COLUMN_MAP`.

## 4. Execution order (so far)

```powershell
venv\Scripts\python.exe scripts\inspect_dataset.py    # schema/timestamp checks -> outputs\metrics\dataset_inspection.json
venv\Scripts\python.exe scripts\feature_dry_run.py    # full-data feature pass, no training -> outputs\metrics\feature_dry_run.json
venv\Scripts\python.exe -m pytest tests -v            # leakage + correctness tests (~3 min, loads the full file once)
```

The feature logic lives in `services\feature_engineering.py`. Every history feature
of a transaction uses only transactions from **strictly earlier minutes**, and the
laundering label is never read. The tests check:
* values worked out by hand on a small fixture;
* label independence;
* that future rows have no effect;
* that same-minute rows are not visible;
* that row order makes no difference;
* that features from a saved history state match a single pass over all data;
* that the results match NetworkX.

### Notebook (run after the dataset is downloaded)

### Using the inference module (this is what Flask calls)

```python
from services.fraud_inference import FraudInference
engine = FraudInference("models")                  # ArtifactError if anything is missing, tampered or incompatible
result = engine.score(raw_df, history=earlier_df)  # raw CSV-shaped rows; history = cleaned rows from the 24h before
result.results        # transaction / graph / combined anomaly scores, risk_level, anomaly_status
result.explanations   # top-3 abnormal features per Suspicious transaction
```
Without `history=`, the saved last 24 hours of the dataset (Sep 10) are used. That only works for batches that start after it.

## 5. Troubleshooting

* **`KeyError: 'Account.1'`.** A different dataset version or export has different headers.
  Edit `COLUMN_MAP` in `config.py`.
* **Bank codes lose leading zeros.** The file was read without `dtype=str` for the bank and
  account columns. Always load through the project's loader.
* **Memory.** The full-data feature pass peaks at about **7.9 GB** of RAM (measured). It
  works on a 16 GB laptop. On an 8 GB machine, close other applications.
